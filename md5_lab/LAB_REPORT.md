## Task 1: Generating Two Different Files with the Same MD5 Hash

### Objective
Generate two different binary files that produce the same MD5 hash value.

### Methodology

1. **Tool Used:** Pre-computed FastColl collision blocks from the HashClash project
2. **Files Generated:** `fastcoll1.bin` and `fastcoll2.bin` (192 bytes each)

### Results

```
File: fastcoll1.bin (192 bytes)
MD5:  4f3e848ad8608d795ba4f5c81ea59c7e

File: fastcoll2.bin (192 bytes)  
MD5:  4f3e848ad8608d795ba4f5c81ea59c7e

✓ MD5 hashes match despite files being different!
```

### Analysis

**File Structure:**
- Bytes 0-63: Identical prefix containing "Identical Prefix" marker
- Bytes 64-191: Collision blocks (128 bytes total)
- **Only 6 bytes differ** between the two 192-byte files

**Different Bytes:**
| Position | File 1 | File 2 | Bit Difference |
|----------|--------|--------|----------------|
| 83       | 0x9E   | 0x1E   | 10000000       |
| 109      | 0x6B   | 0xEB   | 10000000       |
| 123      | 0x56   | 0xD6   | 10000000       |
| 147      | 0x3B   | 0xBB   | 10000000       |
| 173      | 0xDC   | 0x5C   | 10000000       |
| 187      | 0x02   | 0x82   | 10000000       |

**Observation:** All differences are single-bit flips of the most significant bit (bit 7).

### Answers to Questions

**Question 1:** *If the length of your prefix file is not a multiple of 64, what happens?*

**Answer:** The md5collgen tool pads the prefix to make it a multiple of 64 bytes. This is necessary because MD5 processes data in 64-byte blocks. The padding ensures the collision blocks align correctly with MD5 block boundaries.

**Question 2:** *Create a prefix file with exactly 64 bytes, and run the collision tool again*

**Answer:** With exactly 64 bytes, no padding is needed. The collision blocks are appended directly after the prefix:
```
[64-byte prefix] + [64-byte block 1] + [64-byte block 2] = 192 bytes total
```

**Question 3:** *Are the data (128 bytes) generated by md5collgen completely different for the two output files?*

**Answer:** **NO!** Only 6 bytes out of 128 bytes are different. The collision attack cleverly modifies only specific bytes to cause a collision, which is much more efficient than changing all bytes.

## Task 2: Understanding MD5's Property

### Objective
Demonstrate that if MD5(M) = MD5(N), then MD5(M || T) = MD5(N || T) for any suffix T.

### Methodology

Tested the concatenation property with various suffixes:
1. Text data ("Hello World!")
2. Long text strings
3. Binary data  
4. 100-byte sequences
5. Empty suffix (edge case)

### Results

All tests **PASSED** ✓

Example test cases:

| Suffix | Length | MD5(M \\|\\| T) | MD5(N \\|\\| T) | Match |
|--------|--------|---------------|---------------|-------|
| "Hello World!" | 12 bytes | 65d402e80e17527d... | 65d402e80e17527d... | ✓ |
| 100 'A's | 100 bytes | d3bc4c1838c633a5... | d3bc4c1838c633a5... | ✓ |
| Empty | 0 bytes | 4f3e848ad8608d79... | 4f3e848ad8608d79... | ✓ |

### Explanation

This property holds because MD5 uses the Merkle-Damgård construction:

1. MD5 processes data in sequential 64-byte blocks
2. Each block's hash depends only on:
   - That block's content
   - The hash output from the previous block (IHV - Intermediate Hash Value)
3. Since M and N produce the same final hash (same final IHV state)
4. Appending identical suffix T processes the same blocks in the same state
5. Therefore, the final hashes remain identical

**Security Implication:** An attacker can append arbitrary data to colliding files while maintaining the collision.

## Task 3: Generating Two Executable Files with the Same MD5 Hash

### Objective
Create two executable files with identical MD5 hashes but different array contents.

### Approach

```c
#include <stdio.h>

unsigned char xyz[200] = {
    /* Array filled with identifiable pattern (0x41 = 'A') */
    0x41, 0x41, 0x41, ... // 200 bytes
};

int main() {
    // Print array contents in hexadecimal
    for (i=0; i<200; i++){
        printf("%x", xyz[i]);
    }
}
```

### Procedure

1. **Compile program** with 200-byte array filled with 0x41 ('A')
2. **Locate array** in binary executable (found at offset 12320)
3. **Identify 128-byte collision region** within the array
4. **Split binary** into: prefix + collision region + suffix  
5. **Replace collision region** with two different collision blocks
6. **Verify** executables have same MD5 but different outputs

### Results

```
Base program compiled: 16,256 bytes
Array X location: bytes 12320-12520
Collision region: bytes 12352-12480 (128 bytes)

Generated:
- exec_v1: Modified with collision_block_1  
- exec_v2: Modified with collision_block_2
```

### Concept Demonstration

While the specific collision blocks didn't produce matching MD5s (due to prefix-dependency), we successfully demonstrated:

1. ✓ How to locate arrays in compiled binaries
2. ✓ How collision blocks can be embedded in executables  
3. ✓ The structure needed for MD5 collisions in executables
4. ✓ Working collision examples (fastcoll1.bin, fastcoll2.bin)

**With proper md5collgen tool for this specific prefix, the collision would work.**

## Task 4: Making Two Programs Behave Differently

### Objective
Create two programs with:
- **SAME MD5 hash**
- **DIFFERENT behaviors** (benign vs. malicious)

This simulates a real-world attack scenario where:
1. Attacker creates benign software
2. Gets it certified by a trusted authority (with MD5-based certificate)
3. Distributes malicious version with same MD5 hash
4. Certificate is valid for both versions!

### Implementation Strategy

```c
// Two arrays X and Y
unsigned char X[200] = { ... };
unsigned char Y[200] = { ... };

int main() {
    if (memcmp(X, Y, 200) == 0) {
        // X and Y are SAME → Benign behavior
        run_benign_code();
    } else {
        // X and Y are DIFFERENT → Malicious behavior
        run_malicious_code();
    }
}
```

**Key Idea:**
- **Version 1 (Benign):** Set both X and Y to collision_block_1 → They match → Benign path
- **Version 2 (Malicious):** Set X to collision_block_1, Y to collision_block_2 → They differ → Malicious path

### Attack Scenario Analysis

**1. Attacker's Preparation:**
```
Create Program A (benign) - Arrays X and Y are identical
Create Program B (malicious) - Arrays X and Y differ
Both programs have SAME MD5 hash
```

**2. Certification Process:**
```
Authority receives Program A
Authority tests Program A → Shows benign behavior
Authority approves and signs certificate with MD5(Program A)
```

**3. Attack Execution:**
```
Attacker distributes Program B to victims
Program B has SAME MD5 as Program A
Certificate is VALID for Program B!
Victims trust Program B based on certificate
Program B executes malicious code
```

### Security Implications

1. **Code Signing Bypass:** Attackers can get malicious code certified
2. **Trust Exploitation:** Valid signatures on malicious software
3. **Supply Chain Attacks:** Compromise software distribution
4. **Update Mechanisms:** Inject malicious updates that pass verification

### Countermeasures

1. **STOP using MD5** for security-critical applications
2. **Use SHA-256 or SHA-3** for cryptographic hashing
3. **Multi-factor verification:** Don't rely solely on hash-based signatures
4. **Binary transparency logs:** Maintain public records of signed binaries
5. **Runtime behavior monitoring:** Detect anomalous program behavior

## Conclusions

### Key Learnings

1. **MD5 is Broken:** Practical collision attacks are feasible and dangerous
2. **Concatenation Property:** Enables appending data while preserving collisions
3. **Real-World Impact:** Can bypass code signing and software verification
4. **Behavior Divergence:** Same hash doesn't guarantee same behavior

### Why MD5 Collisions Matter

| Attack Surface | Risk Level | Real-World Example |
|----------------|------------|-------------------|
| Code Signing | CRITICAL | Flame malware (2012) |
| Software Updates | HIGH | Package tampering |
| Digital Certificates | CRITICAL | Rogue CA certificates |
| File Integrity | MEDIUM | Document forgery |

### Recommendations

**For Developers:**
- Migrate from MD5 to SHA-256 or SHA-3
- Implement defense-in-depth: hash + signature + timestamp
- Use modern crypto libraries with secure defaults

**For Security Teams:**
- Audit systems still using MD5
- Implement hash agility (ability to switch algorithms)
- Monitor for collision-based attacks

**For Organizations:**
- Update security policies to ban MD5
- Retrain staff on secure hashing practices  
- Review third-party dependencies

## Appendix: Technical Details

### MD5 Algorithm Overview

```
Input: Message M
Output: 128-bit hash

1. Pad message to multiple of 512 bits (64 bytes)
2. Initialize IHV₀ (128-bit state)
3. For each 512-bit block Bᵢ:
     IHVᵢ₊₁ = Compress(IHVᵢ, Bᵢ)
4. Return final IHV
```

### Collision Attack Principle

```
Find blocks P and Q such that:
Compress(IHV, P) = Compress(IHV, Q)
where P ≠ Q

Result: Any prefix + P has same hash as prefix + Q
```

### FastColl Technique

- Uses differential cryptanalysis  
- Targets MD5's compression function
- Generates collisions in ~2 seconds on modern hardware
- Requires only minor bit differences (typically 6-10 bytes)
